# Jarvis2 Android 17 Recovery Implementation Plan

> For agentic workers: use superpowers:executing-plans inline. This side conversation
> prohibits sub-agents and changes to the parent thread's workspace or jobs.

**Goal:** Build and validate a new LineageOS 24 recovery userspace for Jarvis2,
preserving the existing kernel and normal-boot payloads.

**Architecture:** An isolated recovery-only product builds the recovery ramdisk.
A small device UI maps the single physical button into normal recovery menu keys.
A separate offline packer uses AOSP tools to replace only the OEM recovery
fragment. Signing and hardware tests are later, explicitly verified steps.

**Tech stack:** LineageOS 24/AOSP 17 recovery, Soong/Make, C++17, Python 3,
AOSP mkbootimg/unpack_bootimg. ARM64 recovery with the existing 64-bit kernel;
the earlier ARM32 target was superseded by the owner's explicit 64-bit request.

## 1. Locate and pin the baseline

- [x] Read the earlier patched-stock recovery without copying its signing key.
- [x] Record exact manifest/build/recovery revisions in upstream-pins.json.
- [x] Keep all work in a separate source directory and isolated host fixture directory.

## 2. Port the diagnostic recovery UI

- [x] Add a failing host test for missing button mapping.
- [x] Implement tap-next, hold-select, reveal-hidden-menu and delegated other keys.
- [x] Compile the UI source against real pinned LineageOS 24 interface headers.
- [x] Cross-compile an ARM64 ELF object locally using copied Android 14 compiler/
      platform inputs and LineageOS 24 recovery headers. Full Android 17 link remains unverified.
- [x] Inspect the effective saved ramdisk to distinguish its ARM32 userspace from
      AArch64 kernel modules. Add an architecture-gated, non-extracting CPIO auditor.
- [x] Add the Soong module and recovery-only product/board configuration.
- [x] Remove wipe/update menu actions for the diagnostic bring-up.
- [ ] Compile and link the product in a complete, separate Android 17 checkout.
      Validate generated dependencies, init/adbd, SELinux policy and file contexts.
      Do not treat the host syntax check as an Android build.

## 3. Prove offline image packaging

- [x] Test rejection of ambiguous/wrong-type recovery fragments.
- [x] Execute synthetic v4 round trips using AOSP host tools, including paths with spaces.
- [x] Execute an identity round trip of the saved OEM container: protected payloads
      and recognized header fields must match. This uses the existing Android 14
      recovery fragment and is explicitly not a new Android 17 image.
- [ ] Package the actual newly built Android 17 ramdisk and inspect dependencies.
- [ ] Check AVB descriptors/key bindings, budget and rollback behavior offline.

## 4. Hardware gate

- [ ] Audit startup writes to misc/metadata/logs before claiming a read-only RAM test.
      Initial pinned-source findings are in `docs/RAM_STARTUP_AUDIT.md`; the
      assembled init/import/fstab graph and early write guard remain unverified.
- [ ] Prepare an explicit RAM launch and restore procedure using the known kernel.
- [ ] Obtain authorization for the actual hardware test; no flash or slot change
      is implied by source/build work.
- [ ] Verify HDMI, one-button input, USB ADB and return to Android on hardware.
- [ ] Integrate storage, encryption and signed sideload after diagnostic boot works.
